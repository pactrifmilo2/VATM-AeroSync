2. Pipeline xử lý file dữ liệu bay 6 BƯỚC · WORKER

Áp dụng cho file CSV/XLSX/XML/JSON. Thất bại ở bước 1 → thư mục /error/ (FAILED); vi phạm nghiệp vụ ở bước 4 → /quarantine/ (QUARANTINED); ghi DB nguyên khối, rollback toàn phần (BR-02).
FormatValidator
Tồn tại, ≤10MB, UTF-8, header CSV (callsign, from, to, dateflight)
Parser
Strategy CSV/XLSX/XML/JSON → danh sách FlightRow
Normalizer
Trim, UPPERCASE callsign/sân bay, chuẩn hóa múi giờ dateFlight
BusinessRuleValidator
Callsign [A-Z0-9]{2,10}, sân bay [A-Z]{3}, from≠to, ngày bay 2000 → +1 năm
DatabaseWriter
@Transactional: xóa dòng cũ của job → chèn FlightData → SUCCESS
FileArchiver
Chuyển vào processed / error / quarantine; dọn theo BR-03 (60/90 ngày)

3. Luồng xử lý file Word phép bay DOCX · PHÉP BAY CAAV

File .docx phép bay (từ email) đi qua nhánh riêng: nhận diện định dạng bằng hồ sơ YAML → trích xuất phép + lịch bay → đối chiếu sửa đổi → phân giải tàu bay/đường bay → ghi vào bảng ATFM qua PermitImportCoordinator.
📄 File .docx
VD: giangpth_…_LD-3248_34d3f25b.docx
(LD-3248/9/2026VN — Vietjet)
Nhận diện định dạng
So khớp >200 hồ sơ YAML theo priority + detectionPatterns (mã IATA/ICAO, dạng số phép, tiêu đề cột…)
WordPermitFormatDetector · permit-formats/*.yaml
Parse phép + lịch bay
Số phép → normalizedPermitId (VD LD 03248/CHK/2026), bảng lịch bay, mục đích, tàu bay, đường bay
DocxSchedulePermitParser → SchedulePermit
Phân loại phép
Số phép gốc có /S/ hoặc /W/ → phép mùa (SC).
Không có → phép đột xuất (NO)
SchedulePermit.seasonalPermit()
Các bước sau parse (theo thứ tự)
Normalizer → PurposeResolution
Chuẩn hóa dữ liệu, gán mục đích chuyến bay (PAX/CAR…)
RevisionReconciliation
Nếu là REV/RVS: suy số revision, ghép cặp bảng CŨ/MỚI, kế thừa tàu bay & chi tiết từ baseline ATFM, gắn remark ddMMyyyy R(n) (đột xuất) / RVS(n) (mùa)
AircraftType + Via Resolution
Tra loại tàu bay (M_CRAFT_TYPE) và đường hàng không (M_VIA/M_AIRPORT_ROUTE). Bắt buộc với phép dùng kho SC
BusinessRuleValidator
Kiểm tra từng dòng bay; vi phạm → quarantine kèm RowValidationError
PermitImportCoordinator
Khóa Redis theo phép đích → findExisting: trùng hoàn toàn → DUPLICATE; đã có → update; chưa có → insert. Trạng thái lưu vào permit_imports
Định tuyến kho ATFM (usesScheduledStorage)
Số phép có /S/ hoặc /W/ ?
Có → phép mùa
Kho phép mùa (SC)
T_PERMMASTER_SC / T_PERMDETAIL_SC · FLIGHTTYPE=SC · SEASON theo số phép. Sửa đổi tạo phép mới R(n): LD 0001AR2/S/CHK/2026
— nếu Không có S/W —
Có chuyến nào "Hiệu lực từ" ≠ "Hiệu lực đến" ?
Kiểm tra beginDate/endDate của tất cả dòng bay
QUY TẮC MỚI
Tất cả bằng nhau (1 ngày)
Kho đột xuất (NO)
T_PERMMASTER_NO / T_PERMDETAIL_NO · FLIGHTTYPE=NO · ngày bay lưu dạng DAYSFLIGHT. Sửa đổi ghi đè phép gốc, không sinh R(n); mất phép gốc → REVISION_REVIEW
Có ít nhất 1 chuyến khác nhau
MỚI
Kho phép mùa (SC) nhưng FLIGHTTYPE = NO
Toàn bộ phép ghi vào T_PERMMASTER_SC/T_PERMDETAIL_SC với FLIGHTTYPE='NO', id không có season marker (VD LD 03248/CHK/2026).
SEASON tính theo mùa IATA từ ngày bay sớm nhất: CN cuối tháng 3 → CN cuối tháng 10 = S, còn lại = W.
Áp dụng validation nghiêm ngặt như phép mùa (bắt buộc tàu bay + VIA)
Nhãn "MỚI": quy tắc phép đột xuất nhiều ngày (multiDayNonScheduled) bổ sung 09/2026

4. Kết thúc luồng & phản hồi KẾT QUẢ

✅ SAVED / DUPLICATE
Ghi ATFM thành công hoặc phát hiện trùng — file → /processed/
⚠️ QUARANTINED / REVISION_REVIEW
Vi phạm nghiệp vụ hoặc cần xử lý tay — file → /quarantine/
❌ FAILED
Lỗi định dạng/hệ thống — file → /error/, có thể retry từ dashboard
🔔 Cảnh báo + Audit
SyncResultEvent → API AlertService → dashboard; 100% thao tác ghi audit_logs (BR-07)
