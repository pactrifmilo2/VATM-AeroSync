## ATFM INSERT/UPDATE logging

### Objective
Record every ATFM insert/update with timestamps, duration, permit, target table group, generated IDs, row count, result, and technical error details.

### Files changed
- `aerosync-worker/src/main/java/vatm/aerosync/worker/atfm/JdbcAtfmScheduleGateway.java`
- `aerosync-worker/src/main/java/vatm/aerosync/worker/service/PermitImportCoordinator.java`
- `aerosync-worker/src/test/java/vatm/aerosync/worker/service/PermitImportCoordinatorTest.java`
- `aerosync-api/src/main/java/vatm/aerosync/api/service/AuditLogQueryService.java`
- `aerosync-api/src/test/java/vatm/aerosync/api/service/AuditLogQueryServiceTest.java`
- `aerosync-ui/Services/AeroSyncApiClient.cs`
- `docs/plans/19102026-atfm-write-log.md`
- `docs/change-log/19102026.md`

### Before and after
- Before: individual JDBC ATFM writes did not have dedicated start/success/failure application logs and the audit list did not hold full transaction details.
- After: the gateway records `ATFM_DB_WRITE_START`, `ATFM_DB_WRITE_SUCCESS`, and `ATFM_DB_WRITE_FAILURE`, including ISO offset timestamps (Asia/Ho_Chi_Minh), permit, SC/NO tables, duration, generated IDs/row count, and the exception cause chain. The stack trace remains in the worker application log.
- After: every actual write creates `ATFM_INSERT`/`ATFM_UPDATE` or the corresponding failed audit action. Audit persistence errors are logged but do not mask a committed ATFM write or its original failure.
- After: the API exposes `outputSummary` for `ATFM_*`; the UI preserves the technical detail instead of replacing it with a generic reference. Audit records without a linked job now return a null source type without failing the endpoint.
- No password or raw Word content is logged.
